# Extending tools

## Self-hosted live-call tool

Add a versioned pack to `web/lib/voice-tools/extensions.ts`:

```ts
import { defineVoiceToolPack } from "./packs"

export const VOICE_TOOL_PACKS = [defineVoiceToolPack({
  id: "inventory.core",
  version: "1.0.0",
  tools: [{
    name: "lookup_inventory",
    description: "Look up current inventory for one SKU.",
    inputSchema: {
      type: "object",
      properties: { sku: { type: "string" } },
      required: ["sku"],
      additionalProperties: false,
    },
    outputSchema: {
      type: "object",
      properties: { available: { type: "boolean" } },
      required: ["available"],
      additionalProperties: false,
    },
    effect: "read",
    async execute(args, scope, context) {
      return inventory.lookup(scope.orgId, String(args.sku));
    },
  }],
})]
```

Grant `lookup_inventory` in a Flow v2 node or step. The composer binds the pack identity and version into every implementation digest. Bump the pack version whenever imported helpers, dependencies, or authorization behavior change, even if the tool function's source text does not. The registry validates and freezes a provider-neutral JSON Schema subset, rejects catalog collisions and reserved control names, validates arguments and results, and executes only the exact definition pinned into that call's runtime digest. Every admitted descriptor also carries a digest of the complete, sorted extension catalog bound to the call, agent, and organization; a descriptor transplanted from another call or an incomplete catalog fails before availability or dispatch. A later availability change may revoke a tool, but cannot add one to an already-running call.

Executable call runtime snapshots use schema `v: 2`. The legacy-v1 inspection helper exists only for migration and forensics and always returns `executable: false`; it cannot produce a runtime capability. This applies even to a v1 snapshot with an empty extension catalog. Start a fresh v2 call after upgrade instead of substituting a cross-version digest or trying to migrate an in-flight capability.

Flow dispatch uses a two-phase registry boundary. `preflightPinned(...)` checks the exact pinned definition, runtime binding, current availability, and detached input before the receipt is durably marked as dispatched. It returns an opaque, registry-bound, short-lived, single-use capability; only `executePrepared(...)` can consume it after that mark. Admission rejections therefore remain provably `not_sent`, while a failure after the boundary is conservatively treated as indeterminate and reconciled. Integrations must not call an extension directly or re-run preflight after marking dispatch.

Use `isAvailable(scope)` for tenant or feature-gated tools. Declare `effect: "read"` only for genuinely side-effect-free proof tools; `write`, `opaque`, and undeclared effects require a non-`none` Flow v2 idempotency policy. `context.invocationId` and `context.idempotencyKey` are generated by the gateway, never copied from model arguments. Forward them to downstream APIs. Keep authorization in code and data access layers, not descriptions.

Input schemas must have an object root and be acyclic, bounded JSON. Inline references; `$ref`, recursive/dynamic references, regular-expression keywords, and oversized branching are rejected so the same pinned definition can cross OpenAI, xAI, Gemini, and the local gateway. Enforce domain-specific constraints again inside the integration.

## Builder/operator tool

Add an `OperatorToolExtension` to `web/lib/agent/tools/extensions.ts`; the
compiling [membership lookup example](../examples/operator-tools/membership-summary.ts)
shows dependency injection, JSON Schema arguments, and authenticated tenant
scoping. Operator tools receive the authenticated organization, email, focused
agent, and public origin. Their output may also update a surface, flow panel,
notice, or navigation.

Every extension must set `security.tenant_scoped: true` and declare
`security.effect` as `read` or `internal_write`. The exported type requires
both fields and runtime admission rechecks them so untyped JavaScript and unsafe
casts still fail closed. Use `ctx.orgId` from the authenticated execution
context; never accept an organization ID from model arguments.

Registration is not authority for arbitrary egress, spending, or contact with
third parties. Those effects are intentionally absent from the extension
contract and must use a separately authorized capability path. Metadata is an
admission contract, not a sandbox: self-hosted operators remain responsible for
the extension implementation and its data-layer authorization.

## Generated edge tool

The underlying factory can deploy one self-contained `async function run(input, env, context)` to an isolated Vercel project. The current builder capability policy does not expose `create_tool`; a production integrator must first add a funded-approval adapter. `ENABLE_TOOL_FACTORY=true`, `VERCEL_TOKEN`, and the production egress acknowledgements configure infrastructure only and do not grant the model deployment authority. Each organization/tool/revision gets a separate opaque V2 project with automatic system environment exposure disabled. Only vault names declared in `env_var_names` are configured for that project, and `env` is an immutable, prototype-free view of those names.

Each deployed revision gets its own P-256 invocation key. The generated wrapper receives only the public key; the encrypted private key stays in the append-only control-plane revision and is not copied into the mutable tool row. Every request carries a 20-second assertion bound to the exact body, tool, key revision, scope, idempotency key, and stable logical invocation ID. The call snapshot pins only tool ID, endpoint, and key ID, then execution resolves the signer from that exact revision server-side. Framework roots such as `MCP_GATEWAY_SECRET`, provider keys, and Vercel control-plane tokens are never configured in a generated-tool project. Unsigned legacy tools fail closed and must be redeployed.

Generated JavaScript is not a security sandbox. Source validation catches a narrow class of accidental/known ambient-runtime escapes, while the separate deployment is the authority boundary. Code is fully trusted with every explicitly granted vault value and may return, encode, or send it over the network. A secret-bearing revision therefore fails before any database/deploy write unless `GENERATED_TOOL_SECRET_APPROVALS` contains the exact SHA-256 review digest for its organization, slug, source, input schema, and env allowlist. Any source/schema/env change produces a different digest. Grant the narrowest env list and enforce platform egress policy.

Secretless does not mean side-effect-free: code can still send network requests to public systems. Direct `test_tool` execution is therefore disabled for every generated revision; a human label cannot technically make arbitrary JavaScript effect-free. Test through a receipt-backed Flow v2 action with an explicit non-`none` idempotency policy. Revision projects enter a durable cleanup queue before provider deployment; failed and superseded projects are deleted by the scheduler, while retired live revisions receive a 24-hour grace for already-pinned calls. Cleanup retries are bounded and remain visibly `cleanup_required` after exhaustion.

The wrapper's replay cache is process-local defense in depth. Durable Flow v2 receipts provide cross-instance admission/replay authority; end-to-end exactly-once effects additionally require downstream idempotency or authoritative reconciliation. A timeout or lost post-dispatch response is indeterminate and must be reconciled, never blindly retried.

## External MCP server

Use `add_mcp_server` with a label, HTTPS Streamable HTTP URL, explicit `authentication: "none" | "authorization_header"`, and optional exact-case tool allowlist. Public servers are probed before persistence. For `authorization_header`, the tool creates a pending credential slot using only that non-secret sink configuration and automatically opens an ephemeral secure form. The returned `slot_id` identifies intent but has no secret-resolving or consume authority. The authenticated same-origin form creates one browser UUIDv4 `submission_id`, keeps it stable across uncertain retries, and posts `{ slot_id, submission_id, credential }` directly to the trusted finalizer. The finalizer derives the destination from the org-bound slot, accepts only same-submission replay, probes and persists the registration idempotently, and returns status only. A different submission against a completed slot is rejected as already used. The form cannot be pinned or saved as a screen. Plaintext and secret-resolving bearers never enter builder chat, model tool arguments, provider payloads, logs, or chat history.

Successful finalization stores the accepted auth-free catalog revision and returns stable namespaced names such as `mcp_server_<id>_reserve_slot_<hash>`. Put those returned names in Flow v2 `tools`, `action_policies`, and `output_bindings`; attach the returned server ID to the agent. Every granted remote action must have an explicit non-`none` idempotency policy.

MCP `isError: false` proves only that the protocol request returned; it does not prove an opaque mutation reached a terminal downstream state. Until a remote registration carries a trusted, pinned read-back or terminal-ack contract, `run_action` records even a successful remote result as `indeterminate` and does not populate committed output bindings. Use a source extension with an explicit reconciliation query or a signed generated tool for mutations that must complete automatically. This is a deliberate safety boundary, not an exactly-once claim about arbitrary MCP servers.

At call admission the runtime loads the registration-approved catalog, reconnects only to verify the live endpoint still matches it, then pins the sanitized definitions, per-tool schema hashes, allowlist, protocol/server revision, endpoint hash, and encrypted-credential revision into the call's immutable runtime digest. A later call using the same agent version cannot silently accept a new remote interface. Refresh or credential rotation creates a new registry/agent revision. The call snapshot contains an auth reference and a SHA-256 fingerprint of encrypted-at-rest bytes—not the ciphertext and never the decrypted header.

Secured Flow v2 never attaches third-party MCP directly to a model provider. It exposes the same local `run_action` gateway on xAI, OpenAI, and Gemini, checks the step/attempt/epoch-bound capability, atomically reserves a receipt, revalidates the remote catalog, and only then sends `tools/call` from the server. A transport failure—or an MCP `isError` result, which does not prove that a mutating tool made zero downstream changes—leaves the receipt `indeterminate` instead of blindly retrying a possibly committed side effect. Remote error bodies are not echoed; sensitive result keys are redacted before the value reaches the model or receipt.

New approved MCP revisions always use the local server-side proxy, so third-party Authorization never enters provider or browser session configuration and one mutation never appears under both original and namespaced tool names. Remote MCP requires Flow v2 gateway authority; Flow v1 cannot attach a new remote registration. Legacy provider-direct manifests fail closed and must be re-registered; digest compatibility never overrides this credential boundary.

Operational caveats:

- **Production release gate:** set `MCP_EGRESS_ALLOWED_HOSTS` to an exact comma-separated hostname allowlist and set `MCP_EGRESS_NETWORK_GUARD=private-ranges-blocked` only after the deployment network blocks loopback, private, link-local, and cloud-metadata destinations after DNS resolution. Missing, misspelled, or non-matching values disable external MCP before credential decryption or remote I/O. The second setting is operator/deployment evidence, not technical proof; HTTPS-only URLs, redirect rejection, literal-IP blocking, application DNS preflight, and an environment assertion do not by themselves close the socket-layer DNS-rebinding race.
- Stronger self-hosted deployments can inject an address-pinning connector. Its prepared transport returns evidence bound to the exact endpoint, public resolved address set, TLS server name/hostname verification, and blocked redirects; the runtime validates that evidence and uses the connector's paired client factory. The connector remains responsible for actually pinning those addresses. An independently audited egress proxy/firewall is also acceptable and still requires the explicit deployment assertion.
- Endpoint URLs cannot carry query strings, fragments, or userinfo. Put credentials in the vault.
- An explicit empty allowlist means no tools. The server is omitted rather than sending xAI's widening `allowed_tools: []` form.
- Admission caps attached servers, tools, manifest bytes, schema size/depth/branching, action JSON, and operation deadlines. Untrusted regular-expression and reference keywords are rejected; enforce more complex validation inside the MCP server.
- Existing registry rows without an approved catalog must be reconnected/re-registered before use; the runtime fails closed instead of silently blessing their current schema.
- Credential rotation intentionally stops in-flight calls that reference the prior encrypted revision. New calls receive a new snapshot.
- The receipt stores the redacted action value so output bindings and recovery remain deterministic. Do not make an MCP tool return secrets as business data; keep them server-side.

## Adding a realtime provider

Prefer the opt-in [Realtime Provider Plugin v1 contract](../web/lib/realtime/plugins/README.md) for a new adapter. It validates an immutable manifest, transport/media compatibility, lazy credential access, normalized events/tool calls, and provider-neutral tool-result encoding. Run its conformance kit before integration, but treat that as fixture evidence only—not a live provider, latency, quality, or model claim. The contract validates cooperative plugins and is not a sandbox.

The bundled OpenAI, xAI, and Gemini adapters are installed into a protected
server-side runtime registry. A self-hosted deployment can install an
additional adapter during server bootstrap with
`registerRealtimeProvider(...)`; it does not need to edit a core provider
switch or widen the built-in TypeScript union. The registry snapshots public
metadata, rejects duplicate IDs, validates capability/hook consistency, checks
returned browser/server connection metadata, and lets operators unregister
only non-built-in extensions.

Registration deliberately lives in `server-only` code. Provider credentials
must remain behind an ephemeral-token or bridge factory, and an extension must
never return a long-lived provider key in its browser connection payload. A
custom browser transport still needs a matching client-side consumer in the
self-hosted UI. Preserve Flow/MCP semantics, and do not advertise native
telephony unless the adapter declares `native-pcmu`, supplies a direct WSS
endpoint, and actually passes μ-law media end to end. A
`requires-transcoding` adapter cannot register a direct μ-law endpoint.

## Adding a communication provider

Use the [Communication Provider Adapter v1 contract](../web/lib/communications/README.md) for email, SMS, outbound voice, or number purchasing. It binds configuration, provider account, destination, request, integer-micro-USD quote, reservation authority, idempotency, acceptance, and terminal reconciliation evidence.

The adapter contract deliberately lets configuration validation, request preparation, and quoting throw before the durable provider-attempt claim. An integrator must catch and normalize those pre-dispatch exceptions as a definite local rejection/`not_sent` outcome; do not accidentally map them to post-dispatch `indeterminate`. Once the provider dispatch hook is entered, an exception cannot prove absence and remains indeterminate and non-retry-safe.

Twilio and Resend still use their existing operator-action approval, reservation, and settlement paths. They have not migrated to this contract, so the new seam does not yet make those providers configuration-swappable.
